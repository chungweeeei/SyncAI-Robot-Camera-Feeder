# CLAUDE.md

The ROS 2 package `syncai_camera_feeder`, written in Rust (`rclrs` 0.8) with GStreamer
(`gstreamer` / `gstreamer-app` 0.24, built for GStreamer 1.20). It is meant to be the **sole
opener of `/dev/syncai/camera0`**: one capture pipeline whose MJPEG stream is teed to the WebRTC
worker as RTP/JPEG on `127.0.0.1` and to ROS as `sensor_msgs/CompressedImage`. `PROPOSAL.md`
(Chinese) is the design and the source of truth for why it is shaped this way; read it before
changing the architecture.

**Status:** the node is implemented and verified in the Dev Container against a `videotestsrc`
stand-in. It has not yet run against the real camera on the robot (PROPOSAL.md §7 step 2), and
the other repos (worker `rtpjpeg` branch, Workspace bringup, Backend compose) are not changed yet.

Its siblings are SyncAI-Robot-State and SyncAI-Robot-Driver-Manager (also Rust/rclrs); this repo
copies their layout, Dev Container and CI, and their rclrs pitfalls apply here unchanged — see
SyncAI-Robot-State's CLAUDE.md ("rclrs pitfalls") before writing node code.

**The repo root is the package itself** (`package.xml` and `Cargo.toml` are at the root); the
Workspace will pull it into `src/syncai_camera_feeder` with vcstool. `.devcontainer/` is only for
developing this repo on its own. Unlike the siblings there is no `interface.repos`: the node uses
only `sensor_msgs` / `std_msgs`, which the ros2_rust underlay builds.

## Build and test

Everything runs in the Dev Container `syncai-camera-feeder` (VS Code Reopen in Container, or
`devcontainer up --workspace-folder .`). The container's `/workspace` is the named volume
`syncai-camera-feeder_workspace` (build / install / log), and this repo is mounted at
`/workspace/src/syncai_camera_feeder`. The host has no ROS, so `cargo fmt` is the only thing that
works on the host.

```bash
docker exec syncai-camera-feeder bash -lc 'cd /workspace && colcon build --symlink-install --packages-select syncai_camera_feeder'
docker exec syncai-camera-feeder bash -lc 'cd /workspace/src/syncai_camera_feeder && cargo fmt --check'
docker exec syncai-camera-feeder bash -lc 'cd /workspace/src/syncai_camera_feeder && cargo clippy --target-dir /workspace/build/.clippy --all-targets'
docker exec syncai-camera-feeder bash -lc 'cd /workspace/src/syncai_camera_feeder && cargo test --target-dir /workspace/build/.clippy'
```

- `cargo` commands need one `colcon build` first: `/workspace/.cargo/config.toml` is generated by
  colcon-ros-cargo.
- Warnings from `/opt/ros2_rust_underlay/...` (rclrs itself) are not ours; ignore them, and the
  "Patch `<pkg>` was not used in the crate graph" notices too.
- Before finishing, build / clippy / fmt must have zero warnings and all unit tests must pass.
- CI (`.github/workflows/ci.yml`) runs the same commands: `cargo fmt --check` on the bare runner,
  and `.github/scripts/ci.sh` (colcon build, `clippy -- -D warnings`, test) inside the Dev
  Container image. Keep the script and this list in step.

### No camera in the Dev Container

A development machine has no `/dev/syncai/camera0`. Stand in for the camera with the
`source_override` parameter, which replaces the `v4l2src` head of the pipeline:

```bash
ros2 run syncai_camera_feeder camera_feeder_node --ros-args -r __ns:=/default_robot \
  -p "source_override:=videotestsrc is-live=true ! video/x-raw,format=YUY2,width=1280,height=720,framerate=60/1 ! jpegenc"
# then: ros2 topic hz /default_robot/image_raw/compressed
# and:  gst-launch-1.0 udpsrc port=5008 caps="application/x-rtp,media=video,encoding-name=JPEG,payload=26,clock-rate=90000" ! rtpjitterbuffer ! rtpjpegdepay ! jpegdec ! fakesink
```

Keep `format=YUY2` (or `I420`). Left to negotiate, `videotestsrc` picks a format whose JPEG chroma
sampling RTP/JPEG cannot carry, and `rtpjpegpay` rejects every frame with "Invalid component"
while the ROS branch keeps working — which looks like a broken RTP path rather than a test-source
problem. On the robot, add `--device=/dev/syncai/camera0` to
`runArgs` in `devcontainer.json` (it is not there by default because Docker refuses to start a
container whose device is missing).

## Architecture (`src/camera_feeder_node/`)

| File | Responsibility |
| --- | --- |
| `mod.rs` | Wiring: parameters → publisher → pipeline → appsink callbacks → bus watch; `Drop` takes the pipeline to NULL |
| `parameters.rs` | The load-time (read-only) parameters, validated into `Config`; the validators are unit-tested |
| `pipeline.rs` | **Pure** pipeline description and `extra-controls` string; unit-tested |
| `stamp.rs` | **Pure** capture-stamp math (node clock now − frame age on the pipeline clock); unit-tested |
| `bus.rs` | Bus watch thread: WARNING → throttled log; ERROR / EOS → NULL, `exit(1)` for `respawn` |

New logic that can be expressed over plain Rust types goes in a pure module with unit tests.

**Threading:** no rclrs worker or timer. Frames are published from the appsink's GStreamer
streaming thread (an rclrs `Publisher` is an `Arc`, `publish(&self)`), the bus is polled on its
own thread, and the executor only spins so the node is in the graph and serves its parameters.

**Failure handling is "exit and respawn", deliberately.** Any bus ERROR or EOS (device held by
another process, `not-negotiated`, camera unplugged) ends the process with code 1, and the launch
file's `respawn=True` restarts it 2 s later. Do not add in-process pipeline rebuilding: a fresh
process is the one restart that is certain to have released the V4L2 device.

**No hardware acceleration, on purpose.** The pipeline neither decodes nor encodes — JPEG bytes go
from the camera to both branches untouched — so there is nothing for NVJPG/NVENC to do. Keeping
Tegra elements out means the robot container needs no nvidia runtime for this node and the Dev
Container runs the whole pipeline. Transcoding stays in the WebRTC worker.

## GStreamer version pin

The robot container is Ubuntu 22.04 with GStreamer **1.20.3**, and the Tegra elements the WebRTC
worker uses are built against it, so it will not be upgraded. The crates are built with the
`v1_20` feature and nothing newer: a higher feature compiles anywhere and then fails to resolve
symbols when the binary is loaded on the robot. The Dev Container is also 22.04, so it links the
same 1.20.

SyncAI-Robot-Workspace's image currently installs the GStreamer *plugins* but not
`libgstreamer1.0-dev` / `libgstreamer-plugins-base1.0-dev`; those have to be added there before
this package can build in the Workspace (PROPOSAL.md §6.2).

## Real-robot safety

The dev container uses the host network and `ROS_DOMAIN_ID=2`. This node publishes images and
sends UDP to `127.0.0.1`; it commands nothing. But on the robot it **takes the camera**: whichever
of this node, the WebRTC worker's direct-capture branch, `vizionsdk_ros2` or the host's
`publish_camera_crop.sh` opens the device first wins and the rest fail with `EBUSY`. Check
`fuser -v /dev/video*` before starting it on a robot.

## Conventions

- Everything in code and config is written in English: comments, log messages, README /
  CLAUDE.md. Log messages carry a `[Module]` prefix (e.g. `[CameraFeederNode]`). PROPOSAL.md is
  the exception and stays in Chinese.
- Formatting follows the root `rustfmt.toml` (max_width 100); Cargo.toml enables
  `unsafe_code = "forbid"` and `clippy::all`.
- Commits use Conventional Commits (`.github/prompt/copilot-commit-message-instructions.md`), in
  English.
